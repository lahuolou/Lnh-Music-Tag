# 第三方插件 API 与 ZIP 打包规范

## 插件清单

ZIP 根目录应包含 `plugin.json`。示例：

```json
{
  "name": "example.tool",
  "label": "示例工具",
  "kind": "tool",
  "version": "1.0.0",
  "apiVersion": 1,
  "entries": {
    "linux": "bin/example-linux",
    "windows": "bin/example.exe",
    "darwin": "bin/example-macos"
  },
  "panel": "ui/index.html"
}
```

- `name` 仅允许字母、数字、点、下划线和连字符，不能以点开头。
- `kind` 当前支持 `scrape` 或 `tool`。
- `apiVersion` 当前为 `1`。未填写时按 v1 兼容；未知版本拒绝导入。
- `entries` 的路径必须是 ZIP 内相对路径；禁止绝对路径、盘符路径、目录穿越、符号链接和特殊文件。
- `panel` 可选，声明后必须在 ZIP 中存在。
- ZIP 最大 256 MiB、总解压上限 512 MiB、最多 10000 个条目；应避免不必要的大文件。

## 运行协议

宿主以子进程方式执行入口：

```text
<entry> run --input <in.json> --output <out.json>
```

输入 JSON 至少包含 `op`，其他字段作为操作参数传递。入口应把结果写入 `out.json`，并通过退出码表达执行失败。子进程有超时限制；不要依赖宿主的当前工作目录或未声明的环境变量。

## 升级事务

插件更新顺序：

1. 校验压缩包大小、清单、插件名、API 版本、文件数量和路径。
2. 在插件根目录下创建临时 staging 目录，确保临时目录与目标目录处于同一文件系统。
3. 解压并检查入口与面板文件。
4. 将旧目录改名为备份，再将 staging 改名为正式目录。
5. 如果新目录切换失败，恢复旧目录；切换成功后更新注册表并清理备份。

此流程降低升级中断导致插件丢失的概率，但不构成操作系统级沙箱。插件入口仍拥有服务进程用户的文件和网络权限。生产环境应只安装可信插件，并考虑后续加入签名、哈希锁定、权限声明和独立进程隔离。

## 兼容性策略

- v1 的字段采用向后兼容扩展；删除或改变现有字段语义应提升 API 主版本。
- 宿主应拒绝不支持的主版本，并返回可诊断错误。
- 插件开发者应提供最小测试包、升级测试包、路径穿越测试包和异常退出测试。
